V2.0 已上线运行（GitHub Pages / Vercel / Netlify 三平台），支撑办公室物品的登记、借用与归还。经过一段时间实际使用，用户提出三项改进：

2. 物品编号需要手工输入，希望按录入顺序自动生成

## 2. 现状（基于 2026-09-14 代码与线上数据核查）

### 2.1 图片
- 表格视图使用 44×44 裸 `<img>`（`src/pages/ItemListPage.tsx:75`），无预览
- 卡片视图使用裸 `<img>`（`src/pages/ItemListPage.tsx:231`），外层 `<Card>` 挂有 `onClick` 跳转借用页（`src/pages/ItemListPage.tsx:239`）

### 2.2 编号
- `src/pages/ItemFormPage.tsx:169` 的"自动编号"实为伪随机串：
  `code: \`WP${Date.now().toString(36).toUpperCase().slice(-6)}\``
  生成形如 `WP4X2K9A` 的字符串，与用户预期的流水号无关，用户每次手工覆盖
- `items.code` 列**无唯一约束**（`supabase-schema.sql:5`），并发录入可能产生重复编号
- 线上现有 13 条数据编号为 `001`–`013`，**连续无缺口、无重复**
- 编号顺序并非严格按录入时间：`001 绶带` 是第 3 个录入的，说明用户曾手工调整编号顺序
- `createItem()` 接收调用方构造好的完整 Item（`src/services/itemService.ts:121`）

### 2.3 存放位置
- `src/pages/ItemFormPage.tsx:188` 为纯文本输入框，必填
- 线上现有位置写法不统一：12 条为 `综合楼304` 或带后缀的形式，1 条（`008 木头凳子`）仅写 `304`
- 现有位置包含 `综合楼304左侧柜子`、`综合楼304箱子`、`综合楼304右侧柜子以及箱子` 等**带柜位后缀**的写法
- **13 条数据全部位于 304，无一条 302** —— 302 是新启用的存放区域
- `location` 列为 `TEXT NOT NULL DEFAULT ''`，无枚举约束

### 2.4 测试基础设施
- 项目**没有任何测试环境**：`package.json` 无测试依赖、无 `test` 脚本，`src/` 下无测试文件

## 3. 目标与非目标

### 目标
- 图片可点击放大查看，且不影响现有的卡片跳转借用页交互
- 新建物品时自动填入下一个流水编号，用户仍可手动覆盖
- 数据库层面杜绝重复编号
- 存放位置提供常用选项快捷填入，并记住用户最近使用过的完整位置

### 非目标（YAGNI）
- 不引入图片预览第三方库
- 不改造为数据库端编号生成
- 不建立独立计数表
- 不新增物品详情页
- 不安装测试框架
- 不重构与本次三项改动无关的代码

## 4. 设计

### 4.1 图片点击放大

**方案**：用 antd `<Image>` 替换裸 `<img>`。

antd 6.4.4 已安装，`<Image>` 内置点击放大、滚轮缩放、旋转、下载原图、ESC 关闭，零新增依赖。已验证 `<Image>` 由 `antd` 导出（`node_modules/antd/es/index.d.ts:66`），`preview` 属性类型为 `boolean | PreviewConfig`，当前 API 为 `open`/`onOpenChange`（`visible`/`onVisibleChange` 已在 6.x 标记废弃）。

**关键实现细节：阻止事件冒泡**

antd Image 的点击事件会沿 DOM 向上冒泡至外层 `<Card onClick>`，若不拦截，点击图片将**同时**打开预览并跳转借用页。因此必须在外层包裹一层拦截冒泡的元素：

```tsx
<span onClick={(e) => e.stopPropagation()}>
  <Image src={item.photo} preview={{ mask: <EyeOutlined /> }} />
</span>
```

表格视图的 `<tr>` 同样挂有 `onClick`（`src/pages/ItemListPage.tsx:102` 处的按钮已用 `e.stopPropagation()`），故表格视图需同样处理。

**保持不变的部分**
- 卡片视图 `motion.div` 的缩放/光晕动画原样保留，仅替换其中的 `<img>`
- 图片渐进加载机制不变（`fetchItemPhotos()` 异步填充）；图片未加载时组件不存在，自然不可点击
- 无图片物品的 📦 占位符不变
- **尺寸与样式原样保留**：表格视图 44×44、卡片视图撑满容器高度 130 的 `objectFit: 'cover'` 写法均不得改变，仅替换元素本身，避免布局回归

### 4.2 物品自动编号

**架构选择**：前端算号 + 数据库唯一约束兜底。

否决"数据库函数生成"方案的理由：用户选择"自动填但允许手动改"，意味着**前端表单必须预知下一个编号**才能填入。数据库端生成无法免除前端查询，却额外引入 PL/pgSQL 函数的维护与调试成本。前端算号配合数据库 UNIQUE 约束，安全性等价而复杂度显著更低。

**新增文件 `src/lib/itemCode.ts`** —— 纯函数，无副作用

```ts
/**
 * 从现有编号列表中计算下一个可用编号。
 * 仅识别纯数字编号，非数字编号（如用户手打的 "ABC"）不参与计算。
 */
export function nextCode(existingCodes: string[]): string {
  const nums = existingCodes
    .map((c) => c.trim())
    .filter((c) => /^\d+$/.test(c))
    .map(Number);
  const max = nums.length > 0 ? Math.max(...nums) : 0;
  return String(max + 1).padStart(3, '0');
}
```

边界行为：
- 无任何数字编号 → 返回 `001`
- 现有 `001`–`013` → 返回 `014`
- 编号超过 999 → 返回 `1000`（`padStart(3)` 对超长字符串不截断，自然成为 4 位）

**新增服务函数 `fetchNextCode()`（`src/services/itemService.ts`）**

查询全部 `code` 列并交由 `nextCode()` 计算。**该查询刻意绕过 TTL 缓存** —— 若读取缓存数据，刚删除物品后会算出已被占用的编号。

```ts
export async function fetchNextCode(): Promise<string> {
  const { data, error } = await supabase.from('items').select('code');
  if (error) throw error;
  return nextCode((data ?? []).map((r) => r.code as string));
}
```

**⚠️ 并发冲突的两种情形必须区分处理**

数据库加上 UNIQUE 约束后，编号冲突有两种成因，处理方式**相反**：

| 场景 | 正确处理 |
|---|---|
| 自动填入的编号冲突（两人同时录入） | 静默重新取号并重试，用户无感 |
| 用户手动输入的编号冲突（想用 005 但它已存在） | **必须明确报错"编号 005 已存在"**，绝不可静默改号 |

若一律重试，用户手动输入 005 保存后会得到 007，这比报错更糟。

**实现方式**：在 `ItemFormPage.tsx` 用 `useState` 标记编号字段是否被手动编辑过。自动填入时不标记，用户修改时标记。提交时按标记分派：

- 自动编号 + 冲突 → 调用 `fetchNextCode()` 重取，最多重试 3 次
- 手动编号 + 冲突 → 抛出明确错误，表单展示"编号 X 已存在"
- 非冲突错误（如网络故障）→ 直接抛出，不重试

Postgres 唯一约束冲突的错误码为 `23505`，以此判定。

**其他行为**
- 新建页挂载时调用 `fetchNextCode()` 预填编号
- **异步竞态**：`fetchNextCode()` 返回前用户可能已在编号框输入内容。返回时必须先检查手动编辑标记，**若用户已修改则不得覆盖**，否则会把用户输入冲掉
- 编辑页不自动改编号，加载原值，允许用户修改
- 编号查询失败 → 表单提示"自动编号获取失败，请手动填写"，降级但不阻断录入

### 4.3 存放位置快捷选项

**新增文件 `src/lib/locations.ts`** —— 常量 + localStorage 读写

```ts
export const QUICK_LOCATIONS = ['综合楼304', '综合楼302'] as const;

const STORAGE_KEY = 'scau_inventory_recent_locations';
const MAX_RECENT = 4;
```

**界面结构**（`ItemFormPage.tsx` 位置字段下方）

```
存放位置 *
┌────────────────────────────┐
│ 综合楼304左侧柜子|          │
└────────────────────────────┘
 [综合楼304] [综合楼302]        ← QUICK_LOCATIONS 常量
 ─ 最近用过 ─
 [304左侧柜子] [304箱子]        ← localStorage，最多 4 个
```

**行为**
- 点击快捷项 → `form.setFieldValue('location', value)`，随后聚焦输入框并将光标定位到末尾（`inputRef` + `setSelectionRange`），用户可继续输入"左侧柜子"等后缀
- 记忆内容是**用户实际保存成功的完整位置值**，而非按钮文字
- 去重规则：已存在则移至最前，最多保留 4 个
- "最近用过"中与 `QUICK_LOCATIONS` 重复的项不重复展示
- `localStorage` 不可用（无痕模式、隐私设置）→ 全程 try/catch 静默降级，功能不可用但不报错

**两个固定选项写成常量数组**，后续增加存放地点只需修改一行。

## 5. 数据库变更

仅一处变更，**执行前将 SQL 原文交用户确认后再执行**：

```sql
ALTER TABLE items ADD CONSTRAINT items_code_unique UNIQUE (code);
```

前置校验：线上 13 条编号已确认无重复，约束可成功添加。添加后数据库层面不可能出现重复编号 —— 这是比任何前端逻辑都更强的保证，也是本次不引入测试框架仍能保证编号正确性的依据。

**数据订正（待用户确认后执行）**：`008 木头凳子` 的 `location` 为 `304`，与其余数据的 `综合楼304` 写法不一致，拟订正为 `综合楼304`。

```sql
UPDATE items SET location = '综合楼304' WHERE code = '008' AND location = '304';
```

## 6. 错误处理

| 情形 | 处理 |
|---|---|
| 图片加载失败 | antd Image 自带占位表现 |
| 自动编号查询失败 | 表单提示后允许手动填写，不阻断录入 |
| 自动编号重试 3 次仍冲突 | 明确报错，不静默失败 |
| 用户手动编号冲突 | 明确报错"编号 X 已存在" |
| localStorage 读写异常 | try/catch 静默降级，不影响主流程 |

3. 用户验收通过后再推送至 GitHub

## 8. 风险与权衡

| 风险 | 说明与缓解 |
|---|---|
| 事件冒泡导致预览与跳转同时触发 | 已识别，用 wrapper + `stopPropagation` 处理 |
| 前端算号的并发窗口 | 由数据库 UNIQUE 约束兜底，冲突时重试；无测试框架下依赖数据库约束保证正确性 |
| `fetchNextCode()` 全表查询 | 当前 13 条数据可忽略；即使增长至数千条，仅查询单列字符串，开销仍然很小 |
| 位置写法不统一导致快捷填入后与旧数据风格不一致 | 通过第 5 节的数据订正解决历史遗留，新数据由快捷选项统一风格 |
| 渐进加载下图片暂不可点 | 属预期行为，图片填充后即可点击，无需额外处理 |
